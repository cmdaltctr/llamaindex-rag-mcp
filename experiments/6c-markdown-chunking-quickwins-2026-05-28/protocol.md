# Experiment 6c: Quick-Win Interventions for Markdown Chunking on Qasper

**ID**: `markdown-chunking-quickwins-2026-05-28`
**Date**: 2026-05-28
**Operator**: Dr Muhammad Aizat Bin Md Hawari with build agent
**Status**: ACTIVE — follow-up to Experiment 6b's negative result. Same Qasper-dev corpus, same evidence-level metrics, same Pass A / Pass B methodology. Adds four targeted interventions and reports each independently and in combination.
**Related OpenSpec change**: `4-experiment-6c-markdown-chunking-quickwins`

---

## Why this experiment exists

Experiment 6b (`experiments/6b-qasper-markdown-chunking-2026-05-28/`) recorded a real negative result for the heading-aware Markdown chunker (`MarkdownNodeParser → SentenceSplitter`) against the bare `SentenceSplitter` on Qasper-dev. Pass A (reranker off) lost −5.66 pp on Evidence Recall@5; Pass B (reranker on) recovered most of it but stayed at −1.89 pp. Source-level Hit@1 *improved* in both passes (+5.66 pp / +1.89 pp), so the candidate consistently picks the right paper but the wrong section.

The 6b post-mortem and a follow-up multi-source investigation (deep code read, per-query drill, LlamaIndex source review via DeepWiki, literature scan covering Zhou et al. 2026 [1], Bhat et al. 2025 [2], Lu et al. 2025 [4], Prior et al. 2026 [7]) ranked the failure modes. The dominant cause is **chunk fragmentation at fixed `top_k`**: chunk count rose 49% (284 → 424), mean tokens fell 41% (499 → 296), and at `top_k=5` the gold-evidence chunk gets crowded out by sibling chunks from its own paper. The reranker's wider candidate pool (Pass B fetches 50 candidates) recovers ~67% of the loss without any chunker change, which proves the gold chunks are present in the index at ranks 6–15.

Experiment 6c tests four small-bore interventions that the literature and the 6b evidence agree on. Each is independently cheap (under 30 LOC of code or one config flag), each addresses a specific contributing cause, and the combined effect is the experiment's primary research question.

The experiment **deliberately defers** two larger changes — `HierarchicalNodeParser` + `AutoMergingRetriever` and contextual retrieval via local Ollama — to a future OpenSpec proposal. The reasoning is operational rather than technical: both are cross-module changes that require new docstore wiring or a 7–14 minute ingestion latency hit, and we have no evidence yet that the cheap interventions cannot carry us. Saving them keeps the experiment loop tight and the blast radius small.

---

## What this experiment fixes

Experiment 6b answered *whether* the heading-aware chunker beats the bare splitter on a properly evidence-dense corpus. The answer was no, with a clean per-query signature. Experiment 6c answers *which combination of small-bore interventions, if any, flips that verdict*, and produces a recommendation for production defaults.

The corpus, ground truth, embedding model, evaluator code, and Pass A / Pass B methodology are all carried over verbatim from 6b. The only deltas are on the candidate side, and each delta is reported independently so the contribution of each intervention is legible.

## Four interventions (the matrix)

Each intervention is identified by a single letter so factorial runs are legible.

| ID | Intervention | What changes | Lines of code | Failure mode addressed |
| -- | ------------ | ------------ | ------------: | ---------------------- |
| **K** | `top_k` sweep | `run_eval.py --top-k {5, 10, 20}` | 0 (eval flag only) | Cause 1: chunk crowding at fixed `top_k` |
| **C** | candidate-only `chunk_size` | Markdown branch only: `chunk_size ∈ {512, 768, 1024}`, `chunk_overlap=100` | ~3 (one parameter) | Cause 2: smaller chunks lose embedder context |
| **H** | heading content prepend | Prepend `[heading_path] ` to each chunk's text body before embedding | ~10 | Causes 2 & 3 (keyword surface area, heading routing signal) |
| **F** | min-chunk-size floor | Drop or merge chunks below `chunk_size * 0.5` (= 256 tokens at default) | ~15 | Cause 3: orienting `## Introduction` chunks displace evidence |
| **M** | defensive metadata copy | `node.metadata.setdefault("header_path", source_node.metadata["header_path"])` after `_split_sync()` | ~8 | Test-coverage gap; belt-and-suspenders for Section Match@1 |

K is an evaluator-side flag. C, H, F, M are ingestion-side changes that all live in `rag_mcp/ingestion._read_and_chunk_file_async`. F operates after `_split_sync()` returns and before `node.metadata.update(flat_metadata)`.

The two larger changes that are NOT in 6c:

- `HierarchicalNodeParser([1024, 512])` + `AutoMergingRetriever`. Cross-module. Touches `ingestion.py`, `retrieval.py`, the `search()` output shape, and needs a `SimpleDocumentStore` + `StorageContext`. Right answer in principle for "right paper, wrong section" but disproportionate effort if K + C close the gap.
- Anthropic-style contextual retrieval (1–2 sentence chunk summaries from local Ollama `qwen3:0.6b` prepended before embedding). Reported gains are large (35% retrieval-failure reduction in Anthropic's blog) but ingestion latency rises by 7–14 minutes on the 20-paper corpus and `_read_and_chunk_file_async` becomes meaningfully more complex.

Both are referenced in OpenSpec change `4-experiment-6c-markdown-chunking-quickwins/proposal.md` under "Future work" and gated on 6c's outcome.

## Run plan

The runs are factorial-light: not every cell of the K × C grid, but enough to disambiguate the dominant cause from the contributing ones.

## Methodology — preserved from 6b

The two-pass design is the same, the metric set is the same, and the evidence-density guard is the same. The corpus is identical. The only changes are on the candidate side.

### Indexes

`ingest_both.py` from 6b is extended to a parameterised `ingest_candidate.py` that accepts `--chunk-size`, `--heading-prepend`, `--min-size-floor`, `--metadata-copy` flags and writes the candidate to a uniquely named subdirectory under `chroma_candidate_runs/`. The 6b baseline ChromaDB is copied into 6c as `chroma_baseline/` and reused unchanged; 6c never rebuilds the baseline unless an operator explicitly deletes and rebuilds it.

```bash
# Baseline copy (no rebuild)
cp -R experiments/6b-qasper-markdown-chunking-2026-05-28/chroma_baseline \
      experiments/6c-markdown-chunking-quickwins-2026-05-28/chroma_baseline

# Phase 2 example: candidate at chunk_size=768, no other changes
EMBED_MODEL=qwen3-embedding:0.6b \
  uv run python experiments/6c-markdown-chunking-quickwins-2026-05-28/ingest_candidate.py \
    --chunk-size 768 \
    --out-dir experiments/6c-markdown-chunking-quickwins-2026-05-28/chroma_candidate_runs/c768
```

### Pass A and Pass B invocations

```bash
# Pass A — chunker isolation, top_k swept
EMBED_MODEL=qwen3-embedding:0.6b \
  uv run python experiments/6c-markdown-chunking-quickwins-2026-05-28/run_eval.py \
    --pass-name A --rerank off --top-k 10 \
    --candidate-dir experiments/6c-markdown-chunking-quickwins-2026-05-28/chroma_candidate_runs/c768 \
    --output experiments/6c-markdown-chunking-quickwins-2026-05-28/eval_results.2A-c768-k10.json

# Pass B — production shape, top_k swept
EMBED_MODEL=qwen3-embedding:0.6b \
  uv run python experiments/6c-markdown-chunking-quickwins-2026-05-28/run_eval.py \
    --pass-name B --rerank on --top-k 10 \
    --candidate-dir experiments/6c-markdown-chunking-quickwins-2026-05-28/chroma_candidate_runs/c768 \
    --output experiments/6c-markdown-chunking-quickwins-2026-05-28/eval_results.2B-c768-k10.json
```

`run_eval.py` is forked from 6b's evaluator with two added flags:

- `--top-k INT` (default 5): used both for retrieval depth and for `top_k_*` reporting columns. Evidence Recall and section/source diagnostics are computed at this `top_k`.
- `--candidate-dir PATH`: location of the candidate ChromaDB. Default falls back to `./chroma_candidate` for shell-script compatibility with 6b.

The evaluator records the resolved `top_k` and the `candidate_dir` in every output JSON for traceability.

### Metrics — primary and diagnostic

Primary (per category, computed on both passes):

1. **Evidence Recall@K** for K ∈ {1, 3, 5, 10, 20} — fraction of queries where any retrieved chunk up to rank K contains a verbatim evidence sentence (or `expected_answer` when no evidence list is present).
2. **Evidence MRR** — reciprocal rank of the first evidence-bearing chunk.
3. **Section / hierarchy Match@1** — top-1 chunk matches `expected_section` or `hierarchy_path`. Reads structured metadata first; falls back to regex on chunk text only when metadata is missing.
4. **nDCG@5 and nDCG@10** — graded relevance over top 5 and top 10: `2` evidence/section match, `1` same source document only, `0` other.

Diagnostic (reported, not gated):

- Source Hit@1 — kept to expose source-level saturation.
- Chunk count, mean / P95 / max token estimate per index.
- Heading-metadata coverage on candidate chunks (regex-based, the 6b figure for comparability) AND structured-metadata coverage (new — counts chunks where `node.metadata["header_path"]` is non-empty).

### Evidence-density guard

Identical to 6b: ≥ 80% of QA records must carry `evidence_ids`, `evidence_snippets`, or a verifiable `expected_answer`. The 6b corpus already passes at 100%, so the guard is automatic for 6c reuse.

## Pass criteria for 6c

The production decision is made on the **best cell of the matrix**, not on any single intervention. Per-intervention numbers are reported for transparency but the gate is on the best combined configuration.

| Criterion | Threshold |
| --------- | --------- |
| Best-cell heading-targeted Evidence Recall@5 lift, Pass A | candidate − baseline ≥ 0 pp (i.e. parity or better) |
| Best-cell heading-targeted Evidence Recall@5 lift, Pass B | candidate − baseline ≥ 2 pp |
| Best-cell nDCG@5 lift, Pass B | ≥ 0.02 |
| General/evidence-dense Evidence Recall@5 non-regression | candidate ≥ baseline − 2 pp on both passes |
| Candidate chunk size P95 (token estimate) | ≤ `chunk_size * 1.1` for whichever `chunk_size` was used |
| Source-only saturation guard | source Hit@K reported as a diagnostic |

The thresholds are deliberately laxer than 6b's ≥ 5 pp lift target. The 6b target was set under the (now-refuted) assumption that the Markdown chunker was a clean retrieval-quality improvement; 6c's research question is the more modest "can we erase the negative result and ideally reach parity-plus on Pass B".

Interpretation rules:

- If **Phase 1 alone closes the gap** (Pass A and Pass B at parity-or-better with `top_k=10`, no chunker change), recommend `top_k=10` as a deployment knob and ship no ingestion change.
- If **Phase 2 closes the gap** (`chunk_size=768` or `1024` on the Markdown branch only), ship the per-extension chunk-size change and document the new default.
- If **Phase 3 is needed**, ship H (and F if F adds non-trivial lift on top of H). H is preferred over F because it's more reversible (no information is dropped).
- If **none of the four passes closes the gap**, escalate to the deferred big-swing OpenSpec change (HierarchicalNodeParser + AutoMergingRetriever, or contextual retrieval).

## Implementation notes

- The candidate chunker code path lives in `rag_mcp/ingestion._read_and_chunk_file_async`. All 6c interventions are scoped to the `is_markdown` branch — non-Markdown files retain current behaviour.
- The reranker is the cross-encoder (ONNX) shipped under ADR-005, with the wider fetch pool from ADR-016 / OpenSpec change `2-rag-retrieval-quality-improvements`. 6c does NOT change reranker behaviour.
- `retrieval.search()` already exposes the chunk's full `metadata` dict in each result row (see ADR-016), so Section Match continues to read structured metadata first; the regex fallback is unchanged.
- `chunk_size` becomes per-extension at the *call-site* level. The global `CHUNK_SIZE` constant in `config.py` is unchanged and remains the default for the bare-splitter branch. The Markdown branch reads a new optional `MARKDOWN_CHUNK_SIZE` env var (default `CHUNK_SIZE` for backward compatibility).
- Heading prepend (H) writes a `[heading_path] ` prefix to `node.text` *before* embedding. The structured `node.metadata["header_path"]` is unchanged. Section Match@1 still reads `metadata` first.
- Min-size floor (F) drops chunks where `len(node.text) < chunk_size_chars * 0.5`. We use the character estimate (4 chars/token) for consistency with the existing P95 token estimate. Optionally, F can *merge* sub-floor chunks with the preceding sibling instead of dropping; the simpler "drop" variant ships first.
- Defensive metadata copy (M) iterates emitted nodes and runs `node.metadata.setdefault("header_path", node.source_node.metadata.get("header_path", ""))` when `node.source_node` is present. No-op if `header_path` is already set, which is the common case.
