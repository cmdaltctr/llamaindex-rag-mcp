## Context

See proposal.md - Why (ADR-029, the 5-week silent reranker outage). Auditing the codebase for the same shape — catch broad exception, log at WARNING, silently substitute a default, no escalation, no test — found the four items in scope. It also found a working precedent already in the codebase: `VECTOR_STORE` unknown values already raise at compose time with a clear error (ADR-034, Phase 3), and the tripwire for retired env vars (`config/legacy.py`) already establishes "loud failure over silent misconfiguration" as this project's stated value. The provider-selection clamps this change fixes are the *inconsistent* cases — same shape as `VECTOR_STORE`, different treatment.

The audit also surfaced two deliberate, correctly-graceful fallbacks that must NOT change: `DOCUMENT_BACKEND=azure` with missing credentials falls back to local (required by the project's cloud-opt-in hard boundary — CLAUDE.md "⚠️ Ask: Cloud dependencies & API keys — local-first by default... All cloud features must degrade gracefully to local"), and unrecognised `RAG_PROFILE` falls back to `documents` (the profile system's own stated design). Distinguishing "typo produces silently wrong behaviour" from "known failure mode with a deliberate graceful default" is the central judgment call of this change.

## Goals / Non-Goals

**Goals:**
- Implement ADR-029 decision #3 for the reranker: escalate WARNING→ERROR on persistent (not transient) failure, surface it in diagnostics, without making retrieval raise.
- Make composition-root construction failures (embed model, vector store) fail startup instead of continuing in a partially-built state.
- Make provider-selection typos (`EMBED_PROVIDER`, `METADATA_LLM_PROVIDER`, `LOCAL_BACKEND`, `CLOUD_BACKEND`, `RETRIEVAL__HYBRID_SPARSE_BACKEND`, unrecognised `DOCUMENT_BACKEND`) fail startup, matching the existing `VECTOR_STORE` precedent.
- Add test coverage for the `RERANK_ONNX_PROVIDER=coreml` guard (behaviour unchanged, previously untested).
- Fix the threshold-scaling mismatch that applies the ÷30 rerank scaling when reranking was requested but failed, over-permissive by ~30× on exactly the un-reranked scores it should not be scaling.

**Non-Goals:**
- Rewriting the broad `except Exception` blocks in `core/documents/similarity.py`, `core/metadata/*`, `daemon/watcher.py`, `core/vectordb/chroma.py`, or `core/ingestion/writer.py`. None of these are tied to a documented incident; bundling them here couples a precise, incident-anchored change to a broad, noisy one that would need its own risk assessment per file.
- `core/profiles/contract.py`'s safety-contract exception-swallowing (`generate_safety_contract` defaults to `chunk_count: 0` / `old_profile: None` on store errors) — a real finding from the same review, but a different subsystem with no incident behind it. Candidate for a later, separate change.
- `integrations/azure.py`'s "Azure SDK not available … falling back to local" warning. This is the *same policy* as the `DOCUMENT_BACKEND=azure` missing-credentials fallback this change explicitly protects, implemented in a different file — it is covered by the cloud-opt-in-with-local-fallback hard boundary and is correct as-is.
- `core/codebase/codebase_map.py`'s "Magika scan failed … falling back to suffix detection" warning. Same catch→warn→substitute shape, but the fallback is a genuinely equivalent code path (suffix-based file-type detection) rather than a degraded one, and the codebase map is a non-critical accelerator. Low risk, deferred.
- `compose.py::_resolve_active_strategies` silently `continue`s when a configured strategy name is absent from the registry, deferring validation to "the consuming dispatcher" — in a function whose stated purpose is to fail fast on a bad import string. This is the closest missed sibling to the in-scope items, and this change actively sharpens the inconsistency: after §6 the `embeddings` and `llm` entries in that same loop are pre-validated and raise, while `chunking.strategy_fallback` and `metadata.extraction_mode` have **no validation anywhere** and still silently `continue` on a typo.

  It is nonetheless deferred, because "not in the registry" does not mean "invalid": `METADATA__EXTRACTION_MODE=local` is a documented, valid value that is absent from the metadata registry (registered names are `keyword`, `ollama`, `llamacpp`, `llamaindex`, `openrouter`) because that mode is dispatched inline. A naive raise-on-unregistered would break a supported configuration. Separating genuinely-inline modes from typos is real analysis this change has not done, so it is filed as its own work (task 8.6) rather than guessed at here.
- Changing the **value** of the ÷30 rerank-threshold scaling factor or `DOC_SIMILARITY_THRESHOLD` — those are empirically calibrated (CLAUDE.md gotchas #3 and #10) and changing either requires re-running its experiment, not a code guard. Note the distinction from the in-scope item above: this change fixes **when** the ÷30 factor is applied (only on actual rerank success, not on mere intent), and leaves the factor itself at 30.
- Changing `PDF_READER`'s unknown-value handling — it has its own spec (`pdf-reader`) with pre-existing drift (references a `RESOLVED_PDF_READER` module constant that predates the config/compose split) that is out of scope here.
- Changing the two deliberate graceful-degradation policies: `DOCUMENT_BACKEND=azure` missing-credentials fallback, and unrecognised `RAG_PROFILE` fallback.

## Decisions

**Reranker: escalate, don't raise.** The reranker must never abort a search — `search_documents` has to return results even when reranking is completely broken (existing "persistent failure still falls back gracefully" scenario, unchanged). What changes is observability: track consecutive failures with the same error signature (string match on the exception message is sufficient — no need for structured error codes) and escalate the log level from WARNING to ERROR once a threshold is crossed. Reset the counter on any success. Threshold: 3 consecutive failures (matches typical retry/circuit-breaker defaults; not experimentally calibrated, so keep it a named constant, not a new env var — adding a tuning knob for something with no calibration data would be premature configurability).

**The failure counter MUST be module-level, not instance state.** This is the load-bearing decision of the whole change. `core/retrieval/pipeline.py::search` constructs a **fresh reranker on every call** when none is injected (`reranker = _retrieval_get("reranker")()`), and `core/retrieval/registry.py::get` caches the *class*, not an instance. A counter stored on `self` therefore resets to zero on every search and can never reach the threshold — the escalation would be dead code in exactly the default production path where ADR-029's incident occurred. The counter lives in a module-level dict, sibling to `_MODEL_CACHE`, guarded by the existing `_CACHE_LOCK`. (Whether that dict is keyed by model ID is a separate question — resolved below: it is not.)

It must be a *separate* dict, not a field inside `_MODEL_CACHE`: that cache is written only on a **successful** load (`reranker.py`, in the success branch of `_load_model`), so a permanently failing model never gets an entry there and would have nowhere to store its count.

**The counter is a single process-wide count, not keyed by model ID.** Keying by model ID looks tidier but splits the count in practice: `core/retrieval/registry.py` registers the bare class, so the pipeline's `_retrieval_get("reranker")()` constructs with **no** `model_id` and falls back to `DEFAULT_RERANK_MODEL`, while `compose.build_reranker()` passes `settings.retrieval.rerank_model`. An operator running a non-default rerank model would maintain two independent counters, neither escalating as fast as it should. A single counter paired with the error-signature check is the right granularity: the failure mode being defended against (ADR-029) is process-wide, where every call fails identically, and a genuine model switch produces a different error signature which resets the count anyway.

**Both failure paths count, not just inference.** There are two distinct failure shapes and the escalation covers both: inference failure (`rerank()`'s `except Exception`, the ADR-029 CoreML shape) and load failure (`_load_model()`'s `except Exception`, after which `rerank()` early-returns with no log of its own). Because `_load_model` retries on every call, a permanently bad model ID produces exactly the "warning on every call, invisible" pattern this change exists to end — so scoping the counter to the inference handler alone would leave half the incident surface untouched.

**The escalation test must exercise the un-injected path.** The existing regression test `TestPersistentRerankFailureFallback` (`tests/test_retrieval.py`) injects a single failing reranker through the DI parameter, so instance state accumulates across calls within that test. A new escalation test written in the same style would pass while production never escalates — reproducing ADR-029's exact trap (a green test over a broken production path). At least one escalation test SHALL drive `search()` with `reranker=None` so a fresh instance is built per call, proving the counter survives instance churn.

**Surface the failure through `rerank_reason`, and specify who writes it.** `search` already attaches `rerank_reason` under `include_diagnostics=True`, so no new public field is needed. But today that assignment is unconditional and uses the string returned by the *policy resolver*, computed before reranking runs — anything the reranker writes into the result dicts under that key would be overwritten, and `rerank()` returns only `list[dict]`, so it has no other return channel.

Mechanism: `rerank()` records the failure on the instance (e.g. `self.last_failure_reason`, cleared on success), and the pipeline reads it back with `getattr` immediately after the rerank call, overriding the policy string when present. The instance is short-lived, but the pipeline holds it for the duration of the call, so this works even though a fresh reranker is constructed per call. This is deliberately different from where the *counter* lives: the counter must outlive the instance (hence module-level), the reason must not (it describes this one call).

**Fix the threshold-scaling mismatch in the same change.** `_effective_threshold(similarity_threshold, effective_rerank)` scales the similarity threshold down by 30× based on whether reranking was *requested*, not whether it *succeeded*. When the reranker fails, scores remain raw cosine similarity (typically 0.3–0.9) while the threshold drops to ~0.01, so filtering becomes roughly 30× too permissive and noise reaches the caller. This was live on every reranked search throughout the 5-week CoreML outage, silently widening its blast radius beyond "results are not reranked". It is the same silent-degradation class as the rest of this change, it lives in the function this change already edits, and the fix is to pass the actual rerank outcome rather than the intent. Excluding it would mean auditing a function for silent failure and leaving a silent failure in it.

**Deviation from ADR-029 decision #3, stated plainly.** That ADR's third bullet reads: "Log provider failures at ERROR level, not WARNING. A silently failing provider is a production incident, not a transient hiccup." Taken literally, every failure logs ERROR. This change instead logs ERROR only after 3 consecutive same-signature failures. The deviation is deliberate: ADR-029's own first bullet asks to "distinguish transient vs persistent failures", and unconditional ERROR cannot do that — it would fire on the single transient network timeout the reranker is explicitly designed to retry, training operators to ignore the level that is supposed to mean "incident". Thresholded escalation is the synthesis of bullets 1 and 3 rather than a literal reading of 3 alone. The "Resolved by" note added to ADR-029 (task 8.1) SHALL say this, so a later reader does not conclude bullet 3 shipped verbatim.

**Import-time failure is accepted, not an oversight.** `compose.py` calls `ensure_runtime_setup()` at module scope (its last line, with a comment noting it "preserves the pre-refactor side effect"). Once the two construction guards are removed, a provider misconfiguration therefore raises during `import rag_mcp.compose`, not at a controlled startup point — which means `rag-mcp --help` and other commands that never embed anything will also fail. This is accepted for two reasons. First, it is already the shipped behaviour for `VECTOR_STORE`: that check raises from a model validator reached through the same import-time path, so the alternative would leave two fail-loud settings behaving differently. Second, a stderr traceback with a non-zero exit is loud, and loud is the entire point of ADR-029.

Entry-point try/except wrapping was considered and rejected: it does not reliably catch a module-scope import side effect, and it would add debt to work around debt. Moving `ensure_runtime_setup()` out of module scope is the correct fix, but it is a genuine refactor with its own risk profile — it touches the MCP and CLI entry points, the module-scope constructions in `transports/mcp.py`, the experiment runners that import `compose` at module scope, and for consistency the `VECTOR_STORE` path too. An incident-anchored fix should not absorb a general cleanup that is broader than the incident. It is filed as separate work (task 8.4). This note exists so a future audit does not re-flag the same question as an oversight.

**Composition root and provider selection: raise, don't warn-and-clamp.** Two different code paths get the same treatment for the same reason — a process that continues after silently discarding a piece of its own configuration is a process nobody can trust, per ADR-029's core lesson (the warning was real, logged, and still invisible to a production operator). The `VECTOR_STORE` precedent (already raises, ADR-034) is the model: fail at startup with a clear error naming the value and the accepted set, rather than a warning nobody reads on the MCP stderr channel.

**Where the line is drawn.** Two categories of existing fallback exist in `_validate_provider_selections`, and only one changes:
1. **Enum-typo clamps** (`EMBED_PROVIDER`, `METADATA_LLM_PROVIDER`, `LOCAL_BACKEND`, `CLOUD_BACKEND`, `RETRIEVAL__HYBRID_SPARSE_BACKEND`, unrecognised `DOCUMENT_BACKEND`) — the value isn't in the accepted set at all. This is a typo or stale config, structurally identical to the `VECTOR_STORE` case. **Changes to raise.**
2. **Deliberate degrade-gracefully policies** (`DOCUMENT_BACKEND=azure` + missing credentials, unrecognised `RAG_PROFILE`) — the value IS valid, but a downstream precondition isn't met, and the codebase already states in comments why graceful degradation is the intended behaviour (cloud-optional hard boundary; profile system design). **Unchanged.**

`PDF_READER` sits outside both categories — it already has its own capability spec with an explicit warn-and-fallback contract, so changing it here would mean either contradicting that spec (wrong) or rewriting it (scope creep into unrelated doc rot). Left alone.

**Reuse existing diagnostics, don't invent a new channel.** `include_diagnostics=True` and `rerank_reason` already exist in `core/retrieval/pipeline.py::search` (per its docstring). No new public field, no new parameter.

## Risks / Trade-offs

- **[Breaking startup change]** A deployment currently running with a misconfigured provider value (silently clamped today) will fail to start after this change. → Mitigation: this only affects deployments that already have a real, latent misconfiguration — the clamp was masking a bug, not serving a legitimate use case. Document the six affected env vars and their accepted values in `docs/guides/configuration.md`'s migration note. Targets `v3` (the breaking-change branch), where this class of change is expected.
- **[String-match failure signatures are approximate]** Two different underlying errors that happen to produce the same message string will be treated as "the same persistent failure"; two occurrences of the same underlying error with slightly different messages (e.g. an error that embeds a timestamp) won't escalate. → Mitigation: acceptable for a first pass — the goal is "distinguish transient blips from an ongoing outage," not exact error classification. Revisit if it proves too coarse in practice.
- **[Import-time failure widens the blast radius of a config typo]** After task 6, a bad provider value fails during `import rag_mcp.compose`, so commands that never embed anything (`rag-mcp --help`, `list-collections`) also fail, and pytest *collection* — not just execution — breaks for any module importing `compose`. → Mitigation: accepted deliberately (see Decisions). `tests/conftest.py` sets valid provider env vars via `setdefault` before any import, and Ollama embedding construction is lazy with no network call, so the suite is not hostage to a live backend. Task 5.6 asserts collection still succeeds under conftest defaults, which is the specific thing that would silently rot.
- **[Existing tests assert the clamp being removed]** Measured, not predicted: the §6 raises were prototyped against the working tree and the fast suite run, giving **11 failures across 4 modules** (`11 failed, 1095 passed, 1 skipped`). → Mitigation: §7 names every failing test. Note that reading assertions found only 3 of the 4 modules — `tests/test_settings_resolver.py::test_cloud_backend_invalid_value_clamped_to_openrouter` surfaced only by running, which is why the measurement was worth doing rather than reasoning about.
- **[Empty string currently clamps, and would start raising]** The prototype surfaced `RETRIEVAL__HYBRID_SPARSE_BACKEND=""` as an existing parametrised test case. An empty value in `.env` (`SETTING=`) is a normal way operators unset a knob, so raising on it converts a harmless idiom into a startup failure. → Mitigation: task 6.9 treats empty/whitespace as *unset* (fall through to the field default) and raises only on a non-empty unrecognised value. Without that rule the change is gratuitously hostile to a common config habit.
- **[Escalation threshold is a guess, not calibrated]** 3 consecutive failures is a reasonable default but not backed by data the way the ÷30 scaling or `DOC_SIMILARITY_THRESHOLD` are. → Mitigation: keep it a single named constant near the reranker code so it's easy to find and change; do not expose it as a new env var until there's a reason to tune it (Non-Goals).

## Migration Plan

No data migration. Behavioural migration only:
1. Land the reranker escalation change first (Phase 2) — purely additive, non-breaking, no deployment impact.
2. Land the composition-root and provider-selection raise changes (Phase 3) as a single PR, clearly marked BREAKING in the commit/PR description, since they share the same risk profile and the same `v3` target.
3. Update `docs/guides/configuration.md` and `docs/adr/029-...md` (Phase 4) before merge, so the breaking change ships with its migration note already in place rather than as a follow-up.

Rollback: revert the PR. No persisted state changes, so rollback is a plain code revert.
